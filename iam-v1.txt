IAM V1 — Implementation Specification

Build a small but complete IAM platform as a learning project focused on understanding identity, authentication, authorization, security controls, and secure system design.

The goal is not merely to build CRUD APIs. The final V1 must demonstrate a complete secure request flow:

Request
  ↓
Authentication / Session Validation
  ↓
Identify User
  ↓
Authorization
  ↓
Protected Resource / Operation
  ↓
Audit Security-Relevant Result
  ↓
Response

Security controls must be implemented as part of the application control flow rather than added as an afterthought.

14. Security Control Flow

This is a critical architectural requirement.

Every protected request should conceptually follow:

HTTP Request
    ↓
Request validation
    ↓
Authentication / session validation
    ↓
Identify authenticated user
    ↓
Authorization decision
    ↓
Protected operation
    ↓
Audit security-relevant result
    ↓
HTTP Response

Do not perform the protected operation before authorization.

For example:

Request to PATCH /applications/123
        ↓
Validate session
        ↓
Identify user
        ↓
Check application:update
        ↓
IF denied
    → audit authorization denial
    → return 403
        ↓
IF allowed
    → perform update
    → audit operation
    → return response

The authorization check must happen before access to or modification of the protected resource.

15. Authentication vs Authorization

Keep these concepts separate.

Authentication

Answers:

Who are you?

Example:

Session → User 42
Authorization

Answers:

Are you allowed to perform this action?

Example:

User 42
 ↓
Roles
 ↓
Permissions
 ↓
application:deploy
 ↓
ALLOW

Do not combine authentication and authorization into one conceptual mechanism.

16. Authorization Function

Implement centralized authorization logic, conceptually:

authorize(user_id, resource, action)

It should:

Identify the user's roles.
Resolve role permissions.
Determine whether the required permission exists.
Return an allow/deny decision.
Make the decision consistently across protected endpoints.

Do not duplicate authorization logic independently in every endpoint.

However, do not build an unnecessary generic policy framework in V1.

17. Audit Logging Control Flow

Audit logging is a security control and security evidence mechanism, not ordinary application debugging.

It must be integrated into the request flow.

The application should distinguish between:

Application/debug logging

and:

Security audit logging

Security audit events should be generated by trusted server-side code.

Users must never be able to create, modify, or delete audit events through the normal API.

18. Where Audit Logging Happens

Audit security-relevant events at the point where the security decision or security-relevant state change actually occurs.

For an authorization failure:

Request
 ↓
Authenticate
 ↓
Authorize
 ↓
DENY
 ↓
AUDIT AUTHORIZATION_DENIED
 ↓
403

For an authorized operation:

Request
 ↓
Authenticate
 ↓
Authorize
 ↓
ALLOW
 ↓
Perform operation
 ↓
AUDIT operation result
 ↓
Response

For state-changing operations, the audit event should represent the actual result of the operation.

For example:

User role assignment request
        ↓
Authenticate
        ↓
Authorize
        ↓
Perform role assignment
        ↓
If successful → ROLE_ASSIGNED
If failed     → appropriate failure event/error

Do not log a successful state-changing event before the operation has actually succeeded.

19. Authentication Audit Flow

Authentication events are logged around the authentication decision.

Successful login:

Credentials
 ↓
Verify
 ↓
Success
 ↓
Create session
 ↓
LOGIN_SUCCESS

Failed login:

Credentials
 ↓
Verify
 ↓
Failure
 ↓
LOGIN_FAILURE
 ↓
Return generic failure

Repeated failures should also trigger the appropriate security control, such as throttling or temporary blocking.

The audit record should not contain the password.

20. Authorization Audit Flow

Authorization decisions should be auditable.

Example:

User 42
 ↓
GET /applications/123
 ↓
Session valid
 ↓
Check application:read
 ↓
DENY
 ↓
AUDIT AUTHORIZATION_DENIED
 ↓
403

Successful authorization can also be audited where appropriate, particularly for security-sensitive operations.

Do not necessarily create excessive audit noise for every harmless read if that would make the audit trail impractical. Prioritize:

privilege changes
authentication
authorization failures
administrative actions
security-sensitive operations
state-changing operations

22. Audit Event Properties

Audit events should contain enough information to answer:

Who?
What?
When?
Against what?
What was the result?

For example:

user_id: 42
event_type: ROLE_ASSIGNED
target_type: user
target_id: 17
result: success
timestamp: ...
metadata: {
    role_id: 3
}

Do not trust client-provided audit information.

For example, do not allow the client to submit:

{
  "user_id": 999,
  "event_type": "ADMIN_GRANTED"
}

and have the server blindly record it.

Audit events must be generated from trusted server-side context.

23. Audit vs Application Logs

Use security audit logging for events that have security significance.

Use ordinary application logging for things such as:

startup
shutdown
internal diagnostics
unexpected exceptions
database connection problems
debugging information

Do not use ordinary debug logs as a substitute for the security audit trail.

Never put credentials or secrets into either logging mechanism.

24. Error Handling and Audit Ordering

Do not expose raw database errors or internal stack traces to clients.

Use appropriate HTTP responses:

201 Created
204 No Content

400 Bad Request

403 Forbidden
404 Not Found
409 Conflict
429 Too Many Requests

Important distinction:

401 = not authenticated
403 = authenticated but not authorized

For security-relevant failures, ensure the event is captured before returning the response where practical.

Example:

Invalid session
 ↓
Audit security event if appropriate
 ↓
401
Authenticated user
 ↓
Authorization denied
 ↓
AUDIT AUTHORIZATION_DENIED
 ↓
403

Do not return a successful response if the protected operation failed.

30. Security Testing of the Control Flow

Tests should verify not only the final HTTP response but also that the security control occurs in the correct order.

For protected endpoints:

Authentication
    ↓
Authorization
    ↓
Operation

must be enforced.

A request that fails authorization must never reach the protected operation.

For example:

Unauthorized deploy request
        ↓
authorization denied
        ↓
deploy operation must NOT execute
        ↓
AUTHORIZATION_DENIED audit event
        ↓
403

This is important: authorization is a preventative control; auditing is primarily a detective/accountability control.

The audit trail must not be used as a substitute for authorization.

31. Architecture Principle

Keep the following responsibilities separate:

Authentication
    → establishes identity

Session Management
    → maintains authenticated state

Authorization
    → determines what the identity may do

Protected Resource
    → performs the requested operation

Audit Logging
    → records security-relevant decisions and outcomes

Conceptually:

                  ┌──────────────────┐
Request ─────────►│ Authentication   │
                  └────────┬─────────┘
                           │
                           ▼
                  ┌──────────────────┐
                  │ Authorization    │
                  └────────┬─────────┘
                           │
                    ┌──────┴──────┐
                    │             │
                  DENY           ALLOW
                    │             │
                    ▼             ▼
                  Audit       Protected
                  Denied      Operation
                    │             │
                    │             ▼
                    │           Audit
                    │          Result
                    │             │
                    └──────┬──────┘
                           ▼
                        Response

Keep this flow understandable and explicit.

Do not introduce a complex middleware/policy framework merely for abstraction's sake.

Use middleware/dependencies where they genuinely simplify cross-cutting concerns such as session extraction, but keep authorization decisions and security-sensitive behavior easy to trace.

36.1 OWASP Top 10:2025

Explicitly consider and test against all ten OWASP Top 10:2025 categories:

A01 — Broken Access Control

Protect against:

IDOR / BOLA
privilege escalation
missing authorization checks
horizontal privilege escalation
vertical privilege escalation
unauthorized role assignment
unauthorized permission assignment
administrative endpoint bypass
accessing resources belonging to another user
manipulating object IDs to bypass authorization

For this IAM project, this is one of the highest-priority security areas.

Every protected operation must perform authorization before executing the operation.

A02 — Security Misconfiguration

Prevent:

debug mode in inappropriate environments
exposed stack traces
default credentials
hardcoded credentials
overly permissive configuration
unnecessary endpoints
unnecessary services
insecure cookie configuration
overly verbose error responses
insecure CORS configuration where applicable
insecure HTTP security configuration where applicable

Development conveniences must not accidentally become security vulnerabilities.

A03 — Software Supply Chain Failures

Minimize unnecessary dependencies.

For every dependency:

use an established package
keep dependencies explicit
avoid unnecessary packages
avoid abandoned or suspicious packages
pin or constrain versions appropriately
review security implications of dependencies

Do not add a dependency simply to solve a trivial problem that can safely be solved with the standard library.

The project should be able to explain why each significant dependency exists.

Where practical, perform dependency vulnerability scanning as part of the development workflow.

A04 — Cryptographic Failures

Never implement cryptography manually.

Use established, well-reviewed libraries for:

password hashing
cryptographically secure random values
session identifiers

Never:

store plaintext passwords
log passwords
log password hashes
use predictable session IDs
invent custom cryptographic algorithms
use weak hashing algorithms for passwords
use encryption where hashing is required
hardcode cryptographic secrets

Secrets and credentials must never be committed to source control.

A05 — Injection

Protect all externally controlled input.

Consider:

SQL injection
command injection
code injection
LDAP injection in future LDAP functionality
template injection where applicable
log injection

Use parameterized database queries.

Do not construct SQL by concatenating user-controlled strings.

Validate input at application boundaries.

Validation must not be considered a replacement for parameterized queries.

A06 — Insecure Design

Security must be considered during architecture and design.

Before implementing security-sensitive functionality, identify:

assets
actors
trust boundaries
attack surfaces
security assumptions
authorization boundaries
failure modes
abuse cases

Perform lightweight threat modeling for the IAM system.

At minimum, explicitly consider:

Authentication bypass
Authorization bypass
Privilege escalation
IDOR
Session theft
Session fixation
Credential attacks
Role/permission manipulation
Audit manipulation
Database compromise
Sensitive-data leakage

Do not rely on a generic security mechanism to solve an architectural authorization problem.

A07 — Authentication Failures

Implement:

secure password hashing
generic authentication failures
inactive-user blocking
login failure tracking
rate limiting/throttling
temporary blocking or equivalent controls
secure server-side sessions
session expiration
session revocation
logout
session fixation protection

Authentication must not disclose whether a username exists.

Do not build custom cryptographic authentication mechanisms.

A08 — Software or Data Integrity Failures

Protect the integrity of:

authorization decisions
roles
permissions
sessions
audit records
security configuration

Do not trust security-sensitive values supplied by the client.

For example, a client must not be able to submit:

{
  "is_admin": true
}

and thereby become an administrator.

Authorization must be derived from trusted server-side identity and role/permission data.

Audit events must be generated server-side.

A09 — Security Logging and Alerting Failures

Implement security audit logging as a first-class security capability.

Log important:

authentication events
authorization failures
privilege changes
role changes
permission changes
administrative actions
security-sensitive state changes
session security events

Audit logs must answer:

Who?
What?
When?
Against what?
Result?

Never log:

passwords
password hashes
session IDs
authentication tokens
secrets
other credentials

Audit logging must not replace preventive security controls.

The correct flow is:

Authenticate
    ↓
Authorize
    ↓
Prevent unauthorized action
    ↓
Execute authorized action
    ↓
Audit result
A10 — Mishandling of Exceptional Conditions

Handle failures securely.

Do not expose:

stack traces
database errors
SQL statements
internal file paths
secrets
implementation details
authentication information

Use controlled error responses.

Unexpected errors should fail safely.

Security-sensitive operations must not accidentally succeed because an exception occurred.

For example:

Authorization check fails unexpectedly
        ↓
DO NOT continue with operation
        ↓
Fail closed

Do not implement:

if authorization_check_failed:
    continue_anyway()

38. Secure Coding Principles

Apply these principles throughout the implementation.

Least Privilege

Every operation should have the minimum privileges necessary.

Do not give ordinary users administrative capabilities.

Deny by Default

If authorization cannot establish that an action is allowed:

DENY

not:

ALLOW
Fail Securely

Unexpected security failures must not result in access being granted.

Defense in Depth

Do not depend on one security mechanism where multiple independent controls are appropriate.

Example:

Authentication
+
Authorization
+
Database constraints
+
Input validation
+
Audit logging
+
Security testing
Complete Mediation

Authorization must occur whenever access to a protected operation requires it.

Do not authorize once and then assume all subsequent operations are trusted indefinitely.

Separation of Privilege

Keep:

Authentication
Authorization
Application logic
Audit logging

conceptually separate.

Minimize Attack Surface

Only expose endpoints and functionality required by V1.

Do not create unused administrative/debug endpoints.

Secure Defaults

The default state should be secure.

Examples:

users are not administrators by default
permissions are not granted automatically
authorization defaults to deny
accounts are not privileged by default
secrets are not included in responses
debug information is not exposed to clients
Keep Security Logic Centralized

Avoid duplicating authorization logic throughout endpoints.

Use a clear authorization mechanism so security decisions can be reviewed and tested consistently.

40. Secure Development Workflow

Do not implement security only after the application is complete.

For each security-sensitive feature:

Understand requirement
       ↓
Identify security risks
       ↓
Design security control
       ↓
Implement
       ↓
Write functional tests
       ↓
Write security tests
       ↓
Attempt to bypass the control
       ↓
Fix vulnerabilities
       ↓
Add regression test

Use the mindset:

Design
→ Implement
→ Attack
→ Detect
→ Mitigate
→ Retest

42. Security Standard of Completion

Do not interpret "tests pass" as automatically meaning "secure."

V1 is complete only when:

Functional requirements work.
Security controls are implemented.
Security controls are tested.
Known attack paths have been attempted.
Security failures are handled safely.
Security-relevant actions are auditable.
Sensitive information is protected.
The architecture and threat model document the important security boundaries.

The objective is to demonstrate secure engineering, not merely working software.

The project should therefore be treated as a small example of a secure software development lifecycle rather than simply an API CRUD project.
