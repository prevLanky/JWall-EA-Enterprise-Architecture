You are implementing an automated DevSecOps security pipeline for this repository.

## Goal

Build a practical CI/CD security pipeline using open-source/free security tools.

The objective is to automatically identify security vulnerabilities without requiring me to write individual security tests myself.

Use established security scanners and their existing rules/databases rather than creating custom vulnerability tests.

The target security controls are:

* SAST → Semgrep Community Edition
* Secret scanning → Gitleaks
* SCA/dependency scanning → Trivy
* IaC/configuration scanning → Trivy
* Container scanning → Trivy
* SBOM generation → Syft
* DAST → OWASP ZAP
* Security gates → GitHub Actions

Do not introduce commercial SaaS dependencies unless absolutely necessary. If a commercial feature is required for something, stop and explain why before implementing it.

# Phase 2 — SAST

Implement Semgrep Community Edition.

Use existing Semgrep security rules.

Do NOT create a large custom ruleset.

The scan should detect relevant security issues such as:

* injection
* insecure API usage
* dangerous functions
* authentication/authorization mistakes
* common OWASP vulnerabilities
* security anti-patterns

Use rules appropriate for the actual languages/frameworks in this repository.

Generate CI-readable results.

Configure sensible severity handling.

---

# Phase 3 — Secret scanning

Implement Gitleaks.

Scan the repository for:

* API keys
* access tokens
* passwords
* private keys
* credentials
* other high-confidence secrets

Use Gitleaks' existing rules.

Do not print discovered secrets into CI logs.

A confirmed secret finding should fail the appropriate security job.

Do not create unnecessary custom secret patterns.

---

# Phase 4 — Dependency/SCA scanning

Implement Trivy dependency scanning.

Scan the actual dependency ecosystem used by the repository.

Detect:

* known CVEs
* vulnerable dependencies
* vulnerable packages
* severity levels

Use Trivy's vulnerability databases.

Do not manually maintain CVE lists.

Configure an initial security policy where:

* Critical findings → fail
* High findings → fail when appropriate
* Medium/Low → report unless there is a strong reason to block

Adapt this based on the actual project and explain the chosen policy.

---

# Phase 5 — IaC/configuration scanning

If applicable, use Trivy to scan:

* Dockerfiles
* Kubernetes manifests
* Terraform
* cloud configuration
* other supported infrastructure/configuration

Only scan technologies actually present in the repository.

Do not add infrastructure simply for the sake of scanning it.

---

# Phase 6 — Container security

If the application uses Docker:

1. Build the Docker image in CI.
2. Scan the image using Trivy.
3. Fail the security gate according to the documented severity policy.
4. Only allow the pipeline to proceed after the required security checks pass.

Do not use production credentials.

Do not push an image to production before security checks have completed.

If Docker is not applicable, skip this phase and document why.

---

# Phase 7 — SBOM

If practical, generate an SBOM using Syft.

Prefer:

* SPDX
* CycloneDX

The SBOM should represent the actual software artifact being built.

Upload it as a GitHub Actions artifact.

Do not commit generated SBOM files to the repository unless the project already follows that convention.

---

# Phase 8 — DAST

If this repository contains a web application or HTTP API, implement OWASP ZAP.

The intended flow is:

Build application
↓
Start temporary test environment
↓
Wait for application health/readiness
↓
Run OWASP ZAP
↓
Collect findings
↓
Apply security gate
↓
Stop temporary environment

Prefer ZAP Baseline Scan for the initial implementation.

Do NOT scan production.

Do NOT use production credentials.

Do NOT expose the temporary application publicly unless absolutely necessary.

If the application requires authentication for meaningful DAST, document the limitation rather than creating an insecure authentication workaround.

If DAST is not applicable, document why.

---

# Phase 9 — Security gate

Create a clear security gate that evaluates the scanner results.

Use sensible initial thresholds.

Suggested policy:

BLOCK:

* confirmed secrets
* Critical vulnerabilities
* High vulnerabilities with high confidence and clear applicability

REPORT:

* Medium
* Low
* Informational

Do not blindly fail the pipeline on every scanner warning.

Document the policy.

The purpose is to create a realistic DevSecOps security control rather than simply making CI fail constantly.

---

# Phase 10 — GitHub Actions security

If GitHub Actions is used:

Use least-privilege permissions.

Avoid:

```yaml
permissions: write-all
```

Do not use unnecessary write permissions.

Prefer well-maintained official actions.

Avoid floating action references such as:

```yaml
uses: example/action@main
```

Prefer versioned references.

Do not hard-code secrets.

Do not expose secrets through logs.

Do not execute arbitrary downloaded scripts unless absolutely necessary.

Treat the CI/CD pipeline itself as security-sensitive infrastructure.

---

# Phase 11 — Reports

Where practical, upload scanner results as GitHub Actions artifacts.

Useful artifacts include:

* Semgrep report
* Gitleaks report
* Trivy report
* ZAP report
* SBOM

Do not overwhelm normal CI logs with huge scanner outputs.

Make failures understandable.

A developer should be able to determine:

* what tool found the issue
* severity
* affected file/package/endpoint
* why the pipeline failed
* how to investigate it

# Important engineering principles

Keep the implementation simple.

Do NOT:

* rewrite application architecture
* modify unrelated application functionality
* add unnecessary runtime dependencies
* create hundreds of custom security tests
* manually maintain vulnerability databases
* manually maintain large custom security rules
* disable existing tests
* weaken existing security controls
* ignore scanner findings merely to make CI pass
* scan production with ZAP
* hard-code credentials
* commit secrets
* add unnecessary infrastructure
* add commercial tooling without approval
* over-engineer the CI pipeline

The objective is:

> A clean, maintainable, open-source DevSecOps security pipeline integrated into the existing application lifecycle.
