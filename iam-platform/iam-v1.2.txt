# IAM Platform Development Roadmap

You are working on a Python/FastAPI IAM platform intended to evolve from a basic RBAC/authentication service into a realistic enterprise Identity Provider and eventually a broader identity/security platform.

Your job is to implement this **incrementally**. Do not attempt to build the entire roadmap at once.

The most important principles are:

* Keep the implementation simple.
* Prefer modularity over complexity.
* Avoid unnecessary dependencies.
* Do not introduce microservices unless there is a strong architectural reason.
* Build reusable components with clear interfaces.
* Preserve existing functionality unless there is a clear reason to change it.
* Do not rewrite working functionality unnecessarily.
* Security is a core requirement, not something added later.
* Follow OWASP principles, especially OWASP API Security.
* Every security-sensitive decision must be auditable.
* Prefer standards over proprietary designs.
* When there are multiple valid approaches, choose the simplest approach that can evolve later.
* Do not implement future functionality prematurely.

# Phase 0 — Stabilize the IAM Core

Before implementing OAuth/OIDC, inspect the existing architecture.

## Goals

Separate the current `IamService` into logical modules without turning the application into microservices.

Suggested structure:

```text
iam/
├── identity/
├── authentication/
├── authorization/
├── audit/
├── applications/
├── oauth/
├── oidc/
└── tokens/
```

These can remain inside the same FastAPI application.

Do not create network boundaries between them.

The goal is separation of responsibility, not distributed architecture.

### Identity

### Authentication

Responsible for:

* passwords

### Authorization

Responsible for:

### Audit

Responsible for:

* security events

* administrative changes

### Applications

Responsible for:

Later this area will integrate with OAuth clients.

# Phase 0 Security Fixes

Before continuing, review these issues.

## Password hashing

Do not silently fall back to weaker password hashing.

Use a modern password hashing algorithm such as Argon2id.

Password hashing parameters must be configurable and appropriate for production.

Never store plaintext passwords.

## Sessions

Continue using:

* cryptographically random session identifiers
* hashed session identifiers in the database
* expiration
* revocation

Review:

* session fixation
* session replay
* session enumeration
* logout behavior
* concurrent sessions

## Authorization

The current authorization API supports:

```text
authorize(user_id, resource, action, target_id)
```

but `target_id` currently does not meaningfully affect authorization.

Fix this conceptually.

Authorization should eventually answer:

```text
Can SUBJECT perform ACTION on RESOURCE?
```

not merely:

```text
Can SUBJECT perform ACTION?
```

Do not build a complex policy engine yet.

Implement a simple, extensible authorization interface.

# Phase 3 — OAuth 2.0

This is the next major milestone.

The project must transition from being primarily an application-local authentication service into an Identity Provider.

## OAuth clients

Introduce a proper OAuth client model.

At minimum:

```text

client_type
client_secret_hash
redirect_uris
allowed_grant_types
allowed_scopes

```

Support:

* public clients
* confidential clients

Never store client secrets plaintext.

Conceptually:

```text

  ▼

  │ authorization request
  ▼
IAM
  │
  │ authenticate user
  │ authorize client
  ▼
Authorization Code
  │
  ▼

  │

  ▼

  │
```

Validate:

Authorization codes must be:

* short-lived
* single-use
* unpredictable
* bound to the client
* bound to PKCE where applicable

# Phase 4 — Token Service

Create a dedicated token service/module.

It should eventually support:

```text
Access Token
Refresh Token
ID Token
```

Do not mix token generation logic throughout the API routes.

Use a clear interface such as:

```text
TokenService.issue_access_token(...)
TokenService.issue_refresh_token(...)
TokenService.issue_id_token(...)
TokenService.validate_token(...)
```

Exact naming can differ if the existing architecture suggests something better.

---

# Access Tokens

Initially use signed JWT access tokens.

The token should contain appropriate claims such as:

```text
iss
sub
aud
exp
iat
nbf
jti
scope
```

Only include claims that are actually needed.

Access tokens must be:

* audience restricted
* short-lived
* signed
* validated properly

Resource servers must verify:

* signature
* algorithm
* issuer
* audience
* expiration
* not-before where applicable

Never treat decoding a JWT as validation.

---

# Refresh Tokens

Use opaque, cryptographically random refresh tokens.

Store only a secure hash/server-side representation where possible.

Implement:

* expiration
* revocation
* rotation
* replay detection later

Do not make refresh tokens JWTs unless there is a clear architectural reason.

---

# Phase 5 — JWT Signing + JWKS

Implement asymmetric JWT signing.

The IAM must expose:

```text
/.well-known/jwks.json
```

JWKS must contain public signing keys.

JWTs should contain a `kid`.

Implement key rotation in a way that allows old public keys to remain available long enough for existing tokens to validate.

Do not expose private signing keys.

Eventually private keys should be backed by a KMS/HSM rather than application configuration.

---

# Phase 6 — OpenID Connect

After OAuth 2.0 works, add OIDC.

Implement:

```text
/.well-known/openid-configuration
```

and:

```text
/userinfo
```

Add ID token issuance.

Remember:

```text
Access Token
→ intended for APIs/resource servers

ID Token
→ intended for the OIDC client/application
```

Do not use ID tokens as API access tokens.

Implement appropriate OIDC claims without exposing unnecessary personal information.

---

# Phase 8 — Secrets Broker

Do not implement this inside the IAM core.

Create a separate logical platform component:

```text
IAM
 │
 │ identity + authorization
 ▼
Secrets Broker
 │
 ▼
Secret Store
```

The broker should answer:

```text
Who is requesting?
What secret?
For which environment/resource?
Is this identity allowed?
How long should access exist?
```

Initially, integrate with an existing secret store rather than attempting to recreate Vault.

Support eventually:

* static secrets
* dynamic credentials
* secret leasing
* expiration
* revocation
* audit logging

The IAM provides identity/authorization.

The secrets system provides secret storage.

Do not mix those responsibilities.

# Architecture Rules

Before making significant changes, inspect the existing implementation.

Do not blindly create new abstractions.

When implementing a feature:

1. Understand the current architecture.
2. Identify the smallest change that achieves the goal.
3. Reuse existing components where appropriate.
4. Introduce a new module only when responsibility genuinely differs.
5. Keep interfaces replaceable.
6. Add tests.
7. Update documentation.
8. Run the existing test suite.
9. Run security checks.

Avoid:

* unnecessary frameworks
* unnecessary libraries
* premature microservices
* premature event-driven architecture
* complicated policy languages
* implementing a full Vault
* implementing a full CA
* implementing every IAM standard at once

# Working Method

For each phase:

### Step 1 — Inspect

Inspect the current repository and identify:

* relevant modules
* existing interfaces
* database schema
* routes
* tests
* dependencies
* security controls

### Step 2 — Plan

Before modifying code, produce a short implementation plan.

Identify:

* files to change
* database changes
* API changes
* security implications
* tests required

### Step 3 — Implement

Make the smallest coherent change.

### Step 4 — Test

Run:

* unit tests
* integration tests
* relevant security tests
* lint/type checks if configured

### Step 5 — Review

Check for:

* authentication bypass
* authorization bypass
* IDOR/BOLA
* privilege escalation
* token leakage
* secret leakage
* sensitive logging
* insecure defaults
* improper error handling

### Step 6 — Document

Update architecture/API/security documentation where necessary.

# Important Agent Behavior

Do not assume that a feature should be implemented simply because it appears on the roadmap.

The roadmap describes the **target architecture**.

Only implement the current phase.

If implementing a feature requires a significant architectural decision, stop and explain the alternatives before making the change.

Favor:

```text
simple now
+
replaceable later
```

over:

```text
complex now
+
maybe scalable later
```
